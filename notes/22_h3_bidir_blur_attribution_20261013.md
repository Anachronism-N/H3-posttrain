# 22. H3 双向舞蹈微调"脸/手/肢体模糊"：方案总结、10-13 人评与归因对照（2026-10-13）

## 1. 现象
原始 H3 Ref2VA（E3 官方 pipeline + 富文本 VLM prompt）被人工认可可用；所有在我们舞蹈数据上做的双向 LoRA 微调，
都出现脸、手、部分肢体模糊，快动作拖影，且通常训练越久越糊。音频替换（语音/静音）时模型仍然跳舞且仍糊。

## 2. 已尝试方案（按大类，详见 notes/19、20、21）
| 大类 | 做法 | 结果（人评为准） |
|---|---|---|
| 推理设置 | shift 5→12/3、20→50 步、prompt 风格 | 采样器无问题；**清单 caption → 富文本 prompt** 是一大因素（原始 H3 + 富文本 ≈ E3） |
| CFG 蒸馏保护 | H-A 普通 FM → 真 CFG3 可救回；H-A2 DiffSynth 去蒸馏适配器；H-A3 inverse guidance g=4 | 有改善但未通过；两者都用清单 caption 训练，后被否决 |
| 富文本训练 | H-A4 = H-A2 配方 + 富文本侧车（full12k，750 步） | 身份/服饰保持、风格接近 E3，但手脸仍糊 |
| 数据 | H-A5hr 704×1280 原生分辨率；H-A6dup 不插帧（最近帧重复） | 768×1344 推理时手明显清楚；HR/dup 训练结果待人评（dup 1499 已训完，HR 798/1499） |
| AR | H-B2base/B3/B4m（TF/DF 混训、guidance loss、VAE 段对齐分块）、H-C 一致性蒸馏、ODE 轨迹 | TF 目标全部涂抹，停；双向未通过前不再做 AR/ODE |
| 音乐条件 | 节拍写入 prompt、MERT 注入、5 专家 MoE、音乐对比 DPO；富文本版 M1abR/M2bR | 旧清单版结论作废；富文本版 708/886 已出 3case，待人评 |
| 社区方案 | fal Realism LoRA（单用/叠加）、akatz 配方（ostris 助手 + guidance 3.5）、Hybrid BF16（b25–49 AdaLN 合并） | fal 叠加更差排除；后两者纳入 10-13 对照 |
| 同数据 CFG 对照 | 2091 精选、seed42、globalbatch8、300 更新：Hybrid-G3.5/FM、OST1-G3.5/FM、REF-G3.5/FM/inverse3.5、DS-FM/G3.5 | 见 §3 |

## 3. 10-13 人评（同 3 case，富文本，joint + aswap）
- HYB25base（未训练 Hybrid）手部已有些不清晰；HYB25G100/300 比训练前更差，人体整体模糊（最差）。
- OS1G100/300（ostris 助手 + direct3.5）脸/手/部分肢体模糊，但好于 HYB25G。
- REF35（原 Ref2VA + direct3.5，无助手）类似，且 300 比 100 更糊。
- OS1FM（ostris 助手 + 普通 FM）与 OS1G 差不多。

**结论**：助手有/无、FM / direct / inverse guidance、原底座 / Hybrid 全部同样退化且随步数加重 →
**模糊的共性原因不在 CFG 训练方式**。不再新增 CFG/助手/Hybrid 变体；HYB25FM、DSG35、REFINV35 在 216/176/174 步停止
（目录内 `STOPPED_user_cfg_not_key_20261013`，已有 100/200 权重保留）。DSFM8、REFFM 已正常训完 300 作为普通 FM 参照。

## 4. 剩余共性嫌疑与诊断
所有配方共享：训练目标视频（480p 裁剪 + 2/3 RIFE 插帧帧 + 视频 VAE 编码）、LoRA r64 / lr 5e-5、clean 音乐条件、富文本 prompt。
1. **训练目标本身已降级**（最可能解释"越训越像它"）。诊断：`h3ar/diag_decode_train_target.py` 把 3 条快动作训练 latent
   用 VAE 解码 → `logs_omnidance/exp/H3AR/diag_train_target_decode/*_target.mp4`，与同尺寸源片 `*_src.mp4` 对比（待人评）。
2. **微调过程本身**（lr/步数/LoRA 漂移）：与数据无关的退化。
3. 已发现的小不一致：评测音乐 5.06 s < 视频 5.17 s，采样时音频尾部 4 个 latent mask=1 但从不更新（训练时全 clean）。
   原始 H3 同样受影响，不能解释"微调后才糊"；为保持本批可比性暂不修。

## 5. 归因对照：H3 自生成数据（SG512）vs 真实数据（GT512）
- 目的：区分 §4 的 1 与 2。用**原始 H3 Ref2VA 自己生成的视频**作训练目标，其余完全相同。
  若 SG 训练后仍随步数变糊 → 微调过程本身的问题；若 SG 保持清晰而 GT 变糊 → 训练数据降级是根因。
- 数据：2091 精选中每隔 4 取 1 共 512 个 ID（`H3AR/SG512/sg512.txt`，五节点缓存逐字节一致）。
- 生成：`h3ar/sg_gen.py` 在**完全相同的缓存条件**（富文本侧车按 loader 同方式拼接、clean 音乐 mask0、参考锚点）上，
  原始 Ref2VA、无 LoRA、cfg1、官方 shift 12/3、50 步，从噪声采样视频 latent（每 ID 固定种子）。单卡约 11 min/条；
  N1/N3/N4/N7/N8 共 40 卡并行（`h3ar/sg_node.sh`，cephfs mkdir 认领），输出 `H3AR/SG512/lat/`。
  冒烟对照解码：`H3AR/SG512/check_0_1_{sg,gt}.mp4`。
- 训练：`h3ar/sg_build_cache.py` 生成节点本地 `/opt/h3cache/sg512`（input_latents 替换为 SG）与 `gt512`（原样），
  各自带 posi/nega 侧车；两组均 = REFFM 配方（原 Ref2VA、普通 FM、富文本、r64、lr5e-5、seed42、globalbatch8），
  `CFG_REPEAT=5`、300 更新、存 100/200/300。评测同 3 case；SG 组另需对比"SG 数据本身"与其训练结果。
- 注意：512×5 / 8 ≈ 4.7 epoch，比 2091 集 300 步（约 1.15 epoch）重复更多，所以 GT512 必须同时训练作对照，不拿 REFFM 直接比。

## 7. 10-13 晚人评：归因对照全部模糊 → 根因是 FM 微调过程本身
- GT512100、**SG512100**、GT512HI100、GT512LO100、GT512R16100 均"很多模糊"；GT512LR100（lr1e-5）模糊且肢体穿模。
- SG512 的训练目标是原始 H3 自己生成的视频，仍然变糊 → 排除"训练数据降级（480p/RIFE/VAE）"为主因；
  时间段、rank、lr 也都不能解决。结论：对 CFG 蒸馏的 H3 做 FM 回归微调本身会让输出变糊
  （推测：蒸馏后的引导速度场不是线性路径下的 FM 条件期望，回归会把它拉回更"平均"的场；即使目标来自模型自身，单样本 FM 目标的条件期望也不等于蒸馏场）。
- 不再做 FM 类配方/数据/超参变体。SG512/GT512 续训到 600（N4/N6）仅用于确认是否随步数继续变糊。
- 下一步诊断（无需训练，N1/N3/N7/N8 在对照训练结束后自动运行 `h3ar/diag_cfg_after_train.sh`，固定 3 case）：

## 8. 10-14 根因定位（只做推理/数值诊断，不训练）
### 8.1 人评（10-14 凌晨）
- E3 原生 H3 的手部等肢体本身也有模糊；推理 CFG3（去蒸馏底座 / REFFM300 / SG512300）动作变大，但脸手仍糊；
  DSFM8300 与 DSFM8300+保留去蒸馏底座+CFG3 略差于"去蒸馏底座无 LoRA + CFG3"。→ 推理 CFG 只补动作幅度，不补细节。
- 用户决定：300 步效果差的 FM 配方全部放弃（SG512/GT512 续训已停，评测队列已撤）。

### 8.2 自复现（同一缓存条件 + 生成 SG 目标时的同一噪声；`h3ar/sg_gen.py --lora`，`H3AR/DIAG_selfrepro/`）
| 模型 | 与 SG 目标相对距离 | latent 高频能量 / SG 目标 |
|---|---|---|
| 原始 H3 | 0.000（逐位复现） | 1.000 |
| SG512 100 / 300（就在这些目标上训练） | 0.41 / 0.47 | 0.89 / 0.90 |
| GT512 100 / 300 | 0.62 / 0.57 | 0.84 / 0.83 |
| GT512 高噪声半段 / 低噪声半段 / lr1e-5 / r16（300） | 0.58 / 0.55 / 0.53 / 0.55 | 0.83 / 0.87 / 0.86 / 0.83 |
- 推理链路、缓存条件、种子完全一致（原始 H3 逐位复现）→ 不是推理/数据管线 bug。
- 在目标本身上训练 ~5 epoch 仍复现不了、且高频下降 10–17% → FM 损失把模型从它原本的（锐利）轨迹上推开。

### 8.3 速度场探针（8 条训练样本 × 7 个噪声水平；`h3ar/probe_fm.py`，`H3AR/DIAG_probe/`）
- **原始 H3 在它自己的样本上 FM 误差很大，集中在两端**：σ=0.98 时 0.29、σ=0.05 时 0.46（中段 σ=0.5 仅 0.07）。
  即蒸馏后的 H3 不是 FM 最优模型：高噪声时它给出"已经确定的"锐利 x0，而 FM 目标的最优解是条件均值 E[x0|x_t]（必然模糊）。
- 微调后速度改变量 ‖Δv‖/‖v‖ 集中在高噪声：σ=0.98 为 0.24–0.39，σ=0.5 仅 0.04–0.08。
- 预测 x0 的高频能量在 σ=0.98 从 0.055（原始）降到 0.016–0.025（**−55~70%**），σ≤0.3 基本不变。
- 推理用 shift 12、50 步：第 42 步时 σ 才降到 0.70，**84% 的步数在 σ>0.7**，正是被 FM 改成"均值预测"的区间。

→ 损伤来自高噪声步；只在低噪声步用 LoRA ≈ 原始 H3（待人评确认）。

### 8.5 结论（机制）
发布版 H3 经过 CFG/轨迹蒸馏，高噪声步给出"模式化"的锐利预测；FM 回归的最优解是条件均值。任何 FM 梯度——即使目标是模型自己的样本、
只训低噪声段、低 lr、小 rank——都会通过共享权重把高噪声预测拉向均值，而推理的大部分步数正处在高噪声区，于是细节"未被确定"、脸手变糊、越训越糊。
这也解释了 CFG3 只能恢复动作幅度（引导方向）而不能恢复细节。

抽帧（f25/55/85/115）：只在前 10 步（σ>0.98）用 LoRA 就已经换成另一套编排、动作变小；10:30 改变手臂细节；30:47 ≈ 原始 H3。
→ **动作（以及随之而来的手脚平均糊）主要在最前面 σ>0.9 的几步决定**；微调在这里学到的东西 = 对多种可能动作取平均。这也正是"跟音乐跳"需要学习的噪声段——FM 的 MSE 目标在这一段天然与"保持锐利/保持动作幅度"冲突。锚定把这段冻结住，所以既不糊也学不到动作。
下一步方向（待讨论，均是不在 σ>0.9 做 MSE 回归均值的目标）：配对噪声的 reflow 式蒸馏（目标来自比底座更好的教师采样器，噪声与终点一一对应，不取均值）；基于奖励的 RL（节拍对齐 + 手部清晰度，模式寻找）；或 DMD 式分布匹配。

## 12. 10-15 11:20 配对噪声（reflow）对照：直接检验"FM 取条件均值"机制
- 思路：SG512 的目标 x0 是原始 H3 从固定噪声 z（sg_gen seed=sha256(rel)）确定性采出来的。普通 FM 训练用新的随机噪声 ε 构造 x_t，同一个 x_t 对应多个可能 x0 → 最优解是均值（糊、动作小）。若改用生成该 x0 的那个 z（x_t=(1-σ)x0+σz，目标 z−x0），每个样本的目标是确定的，不存在"取平均"。
- 实现：`loss.py` 若缓存条目带 `od_noise` 则用它当噪声；`sg_paired_cache.py` 从 SG512 缓存复制并加入 od_noise（校验 seed 与缓存目标逐位等于 SG 潜变量），sidecar 软链。N4 缓存 /opt/h3cache/sg512p（512 条）。
- 训练 H3REF_sg512p_fm（N4）：与 H3REF_sg512_fm 完全相同（原始底座、480p、lr5e-5、r64、repeat5、seed42、300 步），**只差噪声配对**。
- 第一个读数（step 1，同 batch、同时间步）：loss **0.018**（配对） vs **0.077**（随机噪声）；前 4 步 0.018–0.031 vs 0.077–0.125。即普通 FM 的 loss 中约 3/4 是"给定 x_t 无法确定是哪个 x0"的不可约部分——这部分梯度正是把预测拉向均值的来源。
- 待 step 100/300 视频：若配对组运动比≈1、不糊而普通 SG512 糊 → 机制确认，且得到一条可训练路线：用"更好的样本"（如按节拍对齐挑选的 best-of-N、或音乐引导采样）连同其噪声做配对训练，教模型跟音乐而不取平均。网页【10-15 配对噪声】。

### 13.2 10-15 12:20 下一步：在真实数据上做"配对噪声"训练（GTINV512）

## 14. 10-15 13:00 mentor 讨论：保留 H3 文本空间，把音乐映射到文本空间
mentor 观点（摘要）：
1. 发布的 H3 是蒸馏学生；脱离教师单独用 FM 微调，学生学不到核心判别能力，容易遗忘、趋于平均（其它领域常见）。
2. 策略：尽量不动 backbone 与文本空间；把音乐等条件映射到文本空间（给音乐按 chunk/秒打 caption：节拍位置、动感强度 1–5），等价于"输入音乐 = 输入一段文本"，类似腾讯音乐用 Qwen（非多模态）时把音频映射到文本空间的做法；中间可有 auto-encoder 式的桥。
3. 先验证前提：纯推理下，文本 A（动作相对静止）vs 文本 B（浮夸动作）生成的动作幅度是否明显不同；若是，就能用音乐→文本去控制。

### 15.3 关键新发现：本数据中 GT 舞蹈与音乐能量本身几乎不相关
val47 GT（每条 3 段×1.7 s）：
- 片段级 Spearman(GT 运动量, 音乐 onset 强度) = **0.05**，(运动量, RMS) = 0.02，(运动量, 速度) = −0.18；

→ **"跟音乐跳"在这份数据里本身监督很弱**：舞蹈强弱主要由舞者/编排决定，不由 5 s 内的音乐能量决定。这解释了为什么所有"从数据学音乐跟随"的尝试（MERT/MoE 注入、音乐对比 DPO 准确率≈0.5、E4 Δaudio≈0）都没学到东西——不只是蒸馏学生难训，**目标信号本身就弱**。规则式"响音乐→大动作"的映射也缺乏数据依据。
### 15.4 对路线的影响
1. 画质：冻结 H3（不微调 backbone）是唯一不坍缩的做法；文本是可靠的控制通道。
2. 音乐：可行且有依据的是"音乐 → 片段级风格/速度/段落结构文本"（H3 能执行段级切换）；逐拍对齐需要音乐-动作强相关的数据（AIST++/FineDance 类专业舞蹈，或更长片段、按节拍切分），本数据难以支撑。
3. 若要学习式映射（mentor 的 auto-encoder 桥 / DanceMosaic 的 music tower），先要有能体现音乐-动作对应的数据与指标；否则任何学习方法都会退化为平均。

## 18. 10-15 17:10 方案 A 的学习版：mentor 两阶段"音乐↔文本"自编码器 —— 实验设计
目标：用一个可学习的 music encoder E 把音乐映射成 H3 文本空间里的 K 个 token（替换模板中的逐视频描述），H3 完全冻结。
**阶段 0（今天，CPU，已开跑）——先验证"音乐里有没有文本能描述的信息"**：`music_text_probe.py`，3000 条训练片段，MERT 4 层时间均值 → 线性 logistic，预测该视频 VLM caption 动作段里的 能量（高/低）、速度（快/慢）、舞种 关键词；held-out AUC vs 打乱标签 AUC。若 AUC≈0.5，说明音乐预测不了 caption → 自编码器再好也学不到（与 §15.3 GT 运动-音乐相关≈0 呼应），应先换数据；若显著>0.5，可进入阶段 1。
**阶段 1（重建 + 对齐，H3 不参与，几卡小时）**：
- E：MERT 逐帧特征（或 MERT+节拍）→ Transformer → K=16~64 个 5120 维 token（H3 文本编码器 Qwen3-VL 输出空间）。
- D：token → 重建音乐特征（MERT 时间均值 + onset/节拍包络 + BPM）。损失 = 重建 + **对齐**（E(music) 与该片段真实 caption 的 H3 文本 embedding（已缓存的 posi sidecar `tail`，575×5120）做对比学习 / 均值匹配）。只做重建而不对齐，token 会落在 H3 不认识的区域；对齐保证 token 落在"H3 读得懂的文本流形"上。
- 验收（不跑 H3）：音乐→caption 检索 top-k、重建误差；再把 E(music) 直接塞进 H3 零训练推理 3 case，看换音乐是否改变动作且画质不变（对照：方案 A 规则文本）。
**阶段 2（端到端微调 encoder，H3 冻结）**：E 的 token 接入 pipeline，用视频 FM loss 经冻结 H3 反传只更新 E（类似 textual inversion）。风险与对策：
- 冻结 H3 不会坍缩画质，但 E 可能学到"让 FM loss 最小的平均 prompt"（动作变小）→ 保留阶段 1 的对齐/重建损失作正则、小 lr、监控运动比（§11 指标）与 E4 Δaudio；
- 可只在 σ≥0.5 的高噪声段算 loss（文本主要在这段起作用，§11.1）。
**第二个方向（mentor）：多视角一致的舞蹈视频**——H3/Wan-Dancer 都是单镜头。相关工作：SynCamMaster（ICLR'25，多机位同步生成，UE5 渲染 SynCamVideo 数据集）、ReCamMaster（单视频重渲染新机位，MultiCamVideo 数据集）。舞蹈多视角真实数据：**AIST++**（9 机位同步、10 舞种、带音乐，且音乐-动作强相关，正好补 §15.3 的数据短板）。在 H3 上做同样要冻结 backbone（只加轻量视角条件），且需先确认 H3 的 Ref2VA 能否接受多参考/多视角条件。

**实验规划（按 mentor 方案）**：
- **门控 G0（零训练，N1 跑中）**：冻结 H3，模板 + 只写类别"<Subject 1> dances to {rock / soft piano / hip-hop / traditional Chinese} music."，同 3 case。若 H3 对纯类别文本的动作差异都不大，则后面音频→类别 embedding 也不会有大差异 → 应改用"类别+能量/动作词"作为目标文本。（这一步决定 CLIP 的文本端写什么。）
- **G1 音频↔文本 CLIP（只训音频 encoder）**：文本端 = H3 自己的文本编码器（Qwen3-VL，冻结），输入 H3 模板 +"dances to {类别} music"，取模板中描述 token 段的输出（5120 维）作为该类的目标 embedding；音频端 = 冻结 MERT（或 CLAP 音频塔）+ 可训投影/小 Transformer → 输出同形状 token 序列。数据：pond5 选 6–8 类（rock、hiphop、dance/edm、funk、jazz、piano/ambient/zen、chinese、orchestral），每类等量 ~3k 段×5 s（≈1/3 规模、类别均衡），切 5.17 s 片段。损失：InfoNCE（音频 vs 各类文本 embedding）+ 与本类文本 embedding 的 MSE（保证能直接替换进 H3）。验收：留出集类别 top-1；舞蹈 val 音乐的预测类别分布。
- **G2 替换进 H3（零训练推理）**：把音频 encoder 输出 token 替换 H3 文本编码器在描述段的输出，送入冻结 H3。两极端：一首 rock（或 hiphop）vs 一首钢琴/zen，同人物同 seed，看动作差异（运动比 + 人评）。差异大 → 跑通；再细化为分段能量 caption（§16 方案 A 的学习版）。

### 20.3 caption 里要不要加舞种/动作描述？CLIP 文本无动作或格式不一致会怎样？
- **G0 已证明：H3 对"音乐类别词"几乎不响应（≤13%），只对"动作描述"响应（1.8–2.3×）。** 所以 CLIP 的文本目标如果没有动作描述，即使音频端学得再好，替换进 H3 后也≈G0 的结果（换音乐动作不变）——这是"文本无动作"的问题。
- **格式一致性**：H3 冻结，它只"看得懂"在训练时见过的那种 prompt 位置与写法。我们的做法是把音频 token 写到**文本编码器的输入层**（与真实单词同一位置、同一模板 `<Subject 1> … <Picture 1> … <Audio 1>`），由冻结的 64 层 Qwen3-VL 继续编码 → 等价于"音频变成了一段话"，模板与推理时完全一致。需要保证三处一致：(1) CLIP 目标句的句式 = 推理时插入音频 token 的那一段（同模板同位置）；(2) 推理时不要再附带逐视频富文本——§11.2 已证明富文本会挤占音乐作用（换音乐变化最小）；(3) 若富文本保留，其中不能写与音频冲突的幅度词。
- **之后要不要改训练 caption**：H3 本身冻结，caption 不再用于训练 H3，而是作为**音频 encoder 的监督目标**。要让"什么音乐配什么舞"从数据里学出来（替代我手写的 rock→大动作规则），需要给舞蹈视频重新打**结构化、与 CLIP 目标同格式**的 caption：舞种（固定词表）+ 分段动作强度（平静/中等/夸张）+ 关键动作词；音乐端用同一份视频的配乐。这样音乐 encoder 学到的是"这段音乐 → 这段视频实际的动作描述"。注意 §15.3：本数据集 GT 舞蹈强度与音乐能量相关性很弱（0.05–0.18），所以从本数据学到的映射会偏弱；AIST++/FineDance 的舞种-音乐对应更强。

### 24.1 参考资料要点
- **MotionScript**（IROS'25，github pjyazdian/MotionScript）：输入 3D 骨架序列 → posecode（静态姿态属性，如肘角、手相对关节位置）→ motioncode（posecode 随时间的变化：伸展/弯曲/上升/横移 + 幅度 + 速度）→ 按时间顺序聚合成自然语言（"left elbow extends… a second later she shifts far to the left… speedily"）。**无需训练、规则化、带时间与幅度/速度副词** → 正好解决 §22 "VLM 强度不可靠"：强度直接由关节速度量化。需要 3D 关节（SMPL/HumanML3D 22 关节）。
  - 管线：精选 2091 已有 DWPose 2D → 2D→3D lifting（MotionBERT / VideoPose3D 17 关节，或 GVHMR/WHAM 直出 SMPL）→ 重定向到 MotionScript 的关节定义 → 逐 1.7 s 段生成动作描述。
- **H3 官方 prompt（skills/h3-prompt-writing/references/ref-en.txt）**：Ref2VA 六段顺序 subject_definitions → summary → retention_analysis → detailed_description → overall_soundscape → non_diegetic_music —— **与我们现用模板一致**；`<Audio 1>: fully_copy` 表示音乐 1:1 复用；detailed_description 建议 350–500 词、按播放顺序写动作，镜头切换用 `[Shot N] At MM:SS.mmm`。官方 music-video skill 的做法：先分析 BPM/鼓点/人声时间，把画面动作写到 2–5 s 的分镜里、切点落在拍点上。→ 我们的分段文本（§16/§21）方向一致，但现在描述段过短（~60 词），可按官方建议扩写为时间轴式 350–500 词。
### 24.2 路线（逐步验证，每步都可在冻结 H3 上零训练检验）
1. **音乐 CoT（零训练上限）**：音频大模型（Qwen2.5-Omni-7B，ModelScope 下载中；后续可换 Qwen3-Omni-30B-A3B-Captioner）听 5.17 s 音乐 → 结构化分析（流派、BPM、拍点时刻、能量曲线、段落/drop）→ 同一模型（或文本 LLM）以"编舞师"身份按 H3 官方 Ref2VA 格式写 detailed_description（舞种 + 每段动作，用 MotionScript 风格的部位/幅度/速度词）→ 冻结 H3。验证：同人物换音乐（joint/aswap）动作是否随音乐变化、与规则版方案 A、G2/G3 学习版对比。
2. **音乐专有 encoder（蒸馏 CoT）**：CoT 产出的 H3 文本 embedding 作为目标，训 MERT→H3 文本 token 的 encoder（G1/G3 的连续注入已验证可行）——推理时去掉大模型，速度快、可端到端微调（mentor 阶段 2）。数据：pond5（主力，质量高）+ FMA（开源，下载中）+ 2091 舞蹈配乐。

### 27.3 G4 的真实流程，不是原生音频 encoder 优化
```
旧G4训练：pond5纯音乐 → 冻结MERT → 新E → 32×5120向量
目标：8句“类别+手写动作”的H3词嵌入表token（不是最终文本hidden）

旧G4推理：E输出 → 替换文本embed_tokens中的move占位行 → 冻结文本encoder → H3
原生音乐输入：wav → H3 audio-VAE encoder/pre_block/mean_proj → 32维40Hz声学latent → DiT音频patch投影
```
- 代码证据：`h3ar/genre_ae.py:62-85`、`genre_clip.py:28-39`、`sample_h3_ar.py:98-116`；原生接口见upstream `minimax_h3_audio_vae.py:414-471`。
- G4同时改变数据来源、监督形式、目标空间和注入接口；不是用户要求的“舞蹈配乐、只CLIP、冻结文本/DiT、保持音频推理流程”。因此不能用G4否决该方案。
- 原生H3链路没有另外一个可直接替换的MERT语义encoder；audio-VAE声学latent(32维)与文本hidden(5120维)不同。若优化原生编码侧，训练用的音频侧池化/投影必须明确，推理保留原生32维token与时间网格；不能把5120维CLIP向量直接塞进32维接口。
- CLIP池化对齐不保证原生逐帧token的尺度、声道、时间结构或音频保真兼容。先验证梯度与有限值、分布及重建，再固定3case看音乐控制和画质；不默认检索caption，不自动加视频loss/文本侧可训练头。
- 当前 `ms/clip_train.py` 是MERT独立表征原型，不能因其检索指标改善就宣称原生H3得到收益；未接入的分支不会影响生成。

### 27.12 用户追问音频AdaLN：scheduler time不等于有效音频调制time
- 当前原生audio-VAE CLIP不加载DiT，因此没有扩散timestep/modality输入，也不训练DiT AdaLN；推理沿用原生规则。此前`train_ha.sh`定义的LoRA仅attn qkv/out及mlp fc1/fc2，不包含AdaLN/time_embedder；`train_full.sh --trainable_models dit`的全DiT训练则包括这些权重。权重是否训练与输入time是否变化需分开判断。
- upstream `model_fn_minimax_h3`先转`tau=1-timestep/1000`（pipeline:968-969）；audio位先用tau_audio，然后目标audio中mask=0强制tau=1（1010-1011）；参考audio用max(tau_audio,audio_cond_noise_aug)，默认augment=1故也为1（1014，pipeline:38）。旧`OD_H3_CLEAN_AUDIO=1`训练分支设干净latent与全零mask（loss.py:92-97），所以有效音频调制通常固定在干净端1，虽然外部audio scheduler仍取值。
- modality tag：video=0、text=1、audio=2；DiT用`combined_indices=inverse_indices*3+token_tags`选择各模态AdaLN参数（dit.py:370）。AdaLN projection把time embedding映射成3组×6参数（shift/scale/gate用于attention和MLP，dit.py:166-183,224-234），不是把新增可训练modality embedding简单相加。
- 用捕获DiT入参的CPU小测试验证：raw(video,audio)=(900,700)/(200,100)，真实干净音频与参考音频time均1；视频time0.1/0.8。没有加载/修改DiT权重。
- 发现实际推理边界：三个case音频5.0625s编码203帧，124/24秒视频初始化207帧audio。原生retake unit把补齐的4帧mask设1（pipeline:410-425）；这4帧保留随audio scheduler变化的time，而其他203帧目标audio及203帧参考audio仍time1。采样器只更新video，不更新这4帧audio噪声（sample_h3_ar.py:209-216）。通过真实音频长度+原retake unit的shape stub测试均复现[203,204,205,206]为regenerate tail。
- 因此不能笼统说“全部音频time不变”，也不能直接说time mismatch是音乐控制弱的根因。尾部约0.1s噪声/time不一致是待单变量对照的接口边界，不修改既有运行配置来掩盖；检查padding策略后另列基线与训练encoder相同对照。

### 27.14 固定head与音频尾部对照全部结束（18:00后验收）
- 固定head两组训练退出0，4配置24个推理分片全部退出0并有`[h3ar] done`；24/24新增视频和音轨完整解码通过，均704×1280/24fps/124帧。各6条NLF运动统计退出0；cleanpad组12个分片确认4尾部帧mask改变，训练encoder组18分片确认171张量权重安装。此前42条+本次24条共66条，不增加第四case。
- 固定head结果：平均关节速度3e-7=0.4552、1e-6=0.4530m/s，基线0.4464；aswap/joint速度比3e-7=1.081/0.881/1.210，1e-6=1.107/0.869/1.284，基线=1.092/0.888/1.203。观看joint/aswap同时间抽帧，编排整体仍接近基线；没有明显新舞种/动作控制，也没有可由抽帧证明的整体清晰度提高。固定head未解决“原生编码侧学习增量弱”。
- 尾部策略确实会影响全片（而非只最后0.1s）：原生基线cleanpad/legacy三个joint速度比0.968/1.040/1.019、aswap为0.958/0.957/0.941；已训练全encoder1e-6对应joint0.941/1.092/1.071、aswap1.013/0.990/0.956。1秒后逐帧像素MAE基线4.68–15.73/255，训练encoder4.89–14.25/255。
- 视觉审核：cleanpad可改变手势姿态与动作时相，尤其第一个case aswap的后半段；其他人物总体仍是原来的编舞范围。基线与训练encoder在相同cleanpad策略下仍很相近。该结果不能支持“尾部问题导致音乐条件失效”或“修正即能更贴音乐”。MAE/关节速度只是变化量，不是音乐匹配评分。
- 已提供可验证的尾部处理修正入口`--audio_tail_mode repeat_clean`：重复末个clean音频latent、mask0、有效AdaLN time1。为了保留可复现对照，legacy仍可显式选择且默认不偷换；后续纯音乐条件视频实验可明确使用repeat_clean，并以同策略原生基线重跑，而不是与旧legacy数据混比。未改变原生DiT/audio-VAE架构、训练loss、参考音频长度或输出音轨。
- 新评审preset：“【10-16 原生音频CLIP·固定head】”及“【10-16 音频尾部·单变量】”；显示基线/固定head两组，以及原生/20轮encoder各自legacy vs cleanpad。维持3case、joint/aswap分别看，不把模型变化和尾部政策变化归为同一因素。
- 本批结论：原版MotionScript粒度已被用户认可、训练与接口/权重/解码流程正常，但当前2k、全局池化CLIP及这些学习率配置没有足够证据证明原生音频生成控制改善；大lr带来明显声学漂移。**不称“模型已训好”，也不否定原生encoder路线。** 更换MERT/检索caption/训练DiT不是本轮的解决方案。后续需针对原生编码侧的可学习监督信号和全局池化信息损失单独设计验证，不能靠增加迭代数来掩盖负结果。
