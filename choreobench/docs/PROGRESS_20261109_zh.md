## 2 本轮发现并修复的Windows测试问题

[9eb7d3b的CI](https://github.com/Anachronism-N/H3-posttrain/actions/runs/42591784820)中两个Linux作业成功，两个Windows作业失败。失败位置均为 `tests/test_choreobench_review_page.py` 的两个CLI参数化用例：输出HTML是UTF-8，测试的 `out.read_text()` 却使用系统默认编码。Windows runner的cp1252无法解码中文页面；本机关闭Python UTF-8模式后以GBK也复现同类错误。

修复为 `out.read_text(encoding='utf-8')`，未修改生产页面、生成器或模型逻辑。修复前定向复现2项失败；修复后整个页面测试文件29项通过，运行命令仍显式关闭UTF-8模式，避免环境开关掩盖问题：

```powershell
python -X utf8=0 -m pytest -c choreobench/pytest.ini -q --tb=short tests/test_choreobench_review_page.py
```

修复提交的跨平台结果以关联GitHub Actions为准。旧Linux完整回归通过不等于同期Windows通过，本轮也不把29项页面测试写成全仓库重新验收。

## 3 先评价已经生成的三种条件

令O表示大纲与主题权限，H表示已提交历史。已有输出可回答三个不同问题，无需补齐完整2×2矩阵才开始评价：

| 已有对照 | 评价问题 | 解释限制 |
|---|---|---|
| v11 O+H vs O无H | 固定同一大纲后，历史是否帮助衔接、发展或造成复读 | 每组只有一次整曲解码，不能据单次差异宣布稳定因果收益 |
| v11 O无H vs v17 无O无H | 无历史时，大纲意图和主题权限整体是否有用 | 同时改变主题定义/权限；跨服务session，不是只改一段大纲文字 |
| v17 editor vs no-op | 编辑是否真正降低动作幅度并保留其他事实 | 仅三条狭窄编辑任务；no-op是校准控制，不是最终强编辑baseline |

现有main/独立基线包同时改变O和H，适合问组合系统是否更好；不能把差异全归给history。O无H与无O无H可另从不可变原件构造新的匿名包，不重新生成动作，不改旧绑定或评分。共用计划的多次展示需控制顺序与重复评分，避免将同一计划当新的独立样本。

第一轮优先使用已有v17两套六项包。两名实际评审独立完成生成四维评分和具体时间观察；编辑至少评目标达成、保持性，并检查边界。分别收回评分与观察原件，空值和争议保留。按原逐歌dataset核对design/roster，先输出逐歌问题清单；来源组未审或评分不全时，不绕过比较门槛生成正式排名。

交付物应是一张有具体动作/时间证据的诊断表，说明哪些变化有用、哪些问题普遍存在、哪里无法判断。无需先实现更多平台功能或新增训练。

## 4 最有价值的下一项代码工作

当前接口能处理一歌一编辑任务；扩到每歌多任务、多seed之前，优先补任务身份和分母，而不是增加更多质量总分。

| 次序 | 最小交付 | 验收条件 |
|---|---|---|
| 1 | 独立冻结任务清单与多任务汇总 | 明确dataset/task/源计划/方法/seed身份；未入包、失败、无效、弃权、待评均保留；任务内配对后歌内汇总，旧dataset哈希约束不放宽 |
| 2 | 独立语义裁定文件与联合编辑状态 | 绑定任务和before/after SHA，逐目标保存满足/部分/失败/未知及证据；已知失败优先，全部必要条件满足才成功；不能把整体4分自动当所有语义目标通过 |
| 3 | 已审阅范围与校准统计 | 在明确审阅范围内逐评审算问题区间并集；空issues不当零错误，合理回归不当机械重复 |

目前 [review_analysis.py](../review_analysis.py)以song+method唯一定位计划，同歌同方法的不同task/seed会被拒绝；review-design只检查已进入包的分配，不是独立任务库存。[evaluation.py](../evaluation.py)把语义目标保持pending是正确行为，需有实际独立判断才能接通新的联合成功，而不是改默认值使其通过。

这些扩展应采用新版本文件和汇总接口，兼容旧报告。已有评审无需等待它们；第一轮手工冻结任务库存并逐项核对即可。

## 5 时间菜单实验的进入条件与最小规模

当前 [timing.py](../timing.py)为每个可行动作数生成一套近似均分时间数组，[coordination.py](../coordination.py)要求复制其区间。菜单不读拍点；输入中存在拍点不意味着模型可以生成菜单外切点。v11 main75/76块选3事件，另外两种条件均76/76，不能把三段化单独归因于历史。

v16在预测拍点上找到74/76块的替代切分可行性，这是表达空间诊断，不是质量效果。内部切点与拍点距离也不是BAS，不能由“新切点更接近其构造时使用的拍点”自证改善。

如果听音评价支持时间分配是主要问题，先做局部探针：每首预先指定首/中/末各一块，共9块；A使用原均分排程，B使用预测拍点附近排程，最多18次文本调用、新音频/大纲调用0。先审查这些位置的音乐预测是否可信，固定纳入规则，不根据新输出挑片段。

两臂固定原unit端点、事件数、最短时长、候选、音乐证据、大纲、同一原计划前缀、模型、seed及输出cap；每臂只给一套允许数组。若加入非原网格拍点，两臂共享同一boundary表，仅允许排程不同。无可行替代时按预登记规则回退A并保留分母，不能删掉失败块。两臂输出都不反馈进其他探针的历史。

效果评价检查动作展开时间、音乐转折与衔接，允许平局和无法判断。工程检查确认其余输入一致、范围保护有效和全部成本保留。局部探针不能代替整曲累积效果；若显示收益，再在冻结配置和新歌上检验。

独立冻结前缀探针与新排程入口当前尚未实现，需新合同/目录；不要resume旧v11冒充同一次运行。调用预算用实际请求token测量加输出cap计算，结束后报告usage及实际GPU运行时间，不由token数推租用费用。
